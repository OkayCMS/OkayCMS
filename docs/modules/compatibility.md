# Сумісність модулів OkayCMS

Цей документ описує лише межі сумісності модулів OkayCMS. Загальні правила PHP,
PHPDoc, атрибутів і синтаксису тут не дублюються: для них першоджерелом є
поточний код, типи, PHPDoc і конфігурація проєкту.

## Чекліст модуля

- `Init/Init.php` існує і наслідує `AbstractInit`.
- `Init/module.json` містить метадані модуля.
- Залежності extender-класів із конструктором зареєстровані в `Init/services.php`.
- Smarty-плагіни, маршрути, переклади та шаблони відповідають структурі з
  [опису модулів](README.md) і [швидкого старту](quick_start.md).
- Поля Entity, які додає модуль, створені в БД і зареєстровані в `init()`.
- Runtime-поведінка перевірена в тому самому середовищі, у якому працює основний
  проєкт.

## Специфічні правила OkayCMS

### Масиви в Settings

`Settings::set()` сам серіалізує масиви, а `Settings::get()` повертає їх у початковому вигляді.
Не обгортайте налаштування модуля вручну в `serialize()` або `unserialize()`.

### Chain extensions

Chain extension має повернути отриманий результат методу: змінений або без змін.
Якщо повернення немає, наступні extension не отримають очікуване значення, а
AJAX-поведінка може зламатися без очевидної помилки.

### Extenders із залежностями

Якщо extender має залежності в конструкторі, зареєструйте його в
`Init/services.php`. Однієї реєстрації callback у `Init/Init.php` недостатньо,
щоб контейнер створив цей клас.

### Час валідації

Валідація, що стосується оформлення замовлення, має запускатися лише під час
checkout-дії, а не під час звичайних змін кошика. Перед перевіркою доставки,
оплати або checkout-полів перевіряйте контекст запиту.

### Реєстрація полів Entity

Якщо модуль додає поле до наявної Entity через `migrateEntityField()`, це поле
потрібно зареєструвати в `init()` через `registerEntityField()`, щоб воно
потрапляло в запити Entity.

### Порядок аргументів extender

Extender callback першим аргументом отримує результат оригінального методу,
далі — аргументи оригінального методу в їхньому порядку. Дотримуйтеся контракту
`result + original arguments`.

## Перевірка

Для модулів використовуйте ті самі перевірки, що й для проєкту:

```bash
ddev composer analyze:static
ddev composer test:unit
```

Додавайте вузькі runtime smoke-перевірки, якщо модуль змінює storefront,
адмін-панель, checkout, feed, оплату або доставку.
